# VK Support Analytics & AI Triage Platform

Платформа интеллектуального мониторинга и автоматической маршрутизации обращений пользователей технической поддержки VK. Сервис извлекает структурированную аналитику из неструктурированного текста обращений, классифицирует входящий поток и формирует витрины операционной эффективности службы поддержки в режиме реального времени.

---

## Архитектура системы

Проект спроектирован по модульному принципу с разделением слоев хранения, бизнес-логики и машинного обучения:
- **FastAPI Application Layer:** REST API для CRUD операций и агрегации витрин, работающий с базой данных через асинхронные сессии (`SQLModel` + драйвер `asyncpg`).
- **PostgreSQL 16:** реляционное хранилище обращений с индексацией по ключевым бизнес-полям (`user_login`, `tags`) и фиксацией меток времени для расчета SLA и MTTR.
- **AI Pipeline:** локальный инференс `Qwen2.5-3B-Instruct` под управлением PyTorch на CPU, выполняющий структурированный Zero-shot Triage за один проход.

## Ключевые возможности

### 1. Автономный AI Triage (Классификация без участия пользователя)
Пользователь передает только текст проблемы. Модель `Qwen2.5-3B-Instruct` за один проход инференса извлекает структурированный JSON с пятью ключевыми параметрами:
- **Заголовок инцидента (`title`):** Лаконичное описание сути сбоя (3–6 слов) без потери контекста.
- **Бизнес-тег (`tag`):** Ключевой затронутый сервис или функция платформы (например: «Музыкальная подписка», «Стикеры», «Авторизация»).
- **Тональность (`sentiment`):** Эмоциональный окрас (`positive`, `neutral`, `negative`).
- **Категория инцидента (`category`):** Тип обращения (`bug`, `ui_ux`, `complaint`, `feature_request`, `question`, `other`).
- **Приоритет срочности (`priority`):** Автоматическая оценка критичности инцидента (`high` — финансовые списания, взлом, блокировка; `mid` — стандартные сбои; `low` — идеи и консультации). Защищает очередь от искусственного завышения приоритета пользователями.

### 2. Операционная аналитика службы поддержки
- **MTTR (Mean Time to Resolve):** Среднее время решения и закрытия обращений.
- **SLA Compliance:** Процент обращений с высоким приоритетом, закрытых в нормативные сроки.
- **CSAT Index:** Динамика средней клиентской оценки качества обслуживания.
- **Открытый бэклог:** Контроль очереди необработанных инцидентов.
- **Автоматические продуктовые гипотезы:** Детекция всплесков негатива, аномалий в конкретных модулях и перегрузки очереди.

### 3. Интерактивная витрина и дашборд
- Фильтрация обращений по статусу, приоритету, категории, тональности и полнотекстовому поиску.
- Визуализация структуры обращений на базе графиков Plotly.js (распределение категорий, тональности, динамика по датам, топ тегов).
- Управление жизненным циклом обращения (перевод в работу, закрытие с фиксацией времени).
- Экспорт реестра обращений в формате CSV (UTF-8 BOM).

## Стек технологий

- **Язык и среда:** Python 3.11, менеджер пакетов `uv`.
- **Бэкенд-фреймворк:** FastAPI, Uvicorn, Pydantic V2.
- **База данных и ORM:** PostgreSQL, SQLModel, SQLAlchemy 2.0 (асинхронный драйвер `asyncpg`).
- **Machine Learning / NLP:** Hugging Face `transformers`, PyTorch, токенизатор Qwen2.5.
- **Фронтенд:** Vanilla JavaScript (ES6+), CSS3 (Enterprise Light Theme), Plotly.js.

## Этапы разработки и инженерные решения

В ходе проектирования и реализации платформы были решены следующие инженерные задачи:

1. **Миграция и выбор языковой модели:**
   - Первоначально рассматривались классические Seq2Seq архитектуры (T5 / RuT5) и эвристические парсеры на базе морфологического анализа (`pymorphy3`). На тестах выявлена склонность малых Seq2Seq моделей к галлюцинациям в заголовках и захват случайных вводных слов («Добрый вечер», «Здравствуйте») вместо бизнес-тегов.
   - Система переведена на декодерную модель нового поколения `Qwen2.5-0.5B-Instruct` с применением Chat Templates (`apply_chat_template`) и детерминированной генерации (`do_sample=False`).

2. **Защищенный структурированный инференс (Structured Output Extraction):**
   - Реализована генерация единого JSON-объекта со всеми метаданными тикета за один вызов модели, что сократило время обработки обращения на CPU до ~1.5–2 секунд.
   - Внедрен механизм защитного парсинга (Defensive JSON Parsing): поиск крайних границ фигурных скобок и безопасный fallback при повреждении структуры ответа, предотвращающий падение бэкенда с кодом 500.

3. **Оптимизация базы данных и асинхронного цикла:**
   - Модели данных разделены на DTO-схемы ввода (`TicketCreate`), таблицы хранения (`Ticket`) и схем обновления (`TicketUpdate`), что исключило перезапись неизмененных полей при PATCH-запросах.
   - Тяжелые вычисления аналитических срезов и инференс нейросети вынесены в отдельные пулы потоков через `asyncio.to_thread`, исключая блокировку главного Event Loop приложения.

4. **Интерфейс и продуктовый дизайн:**
   - Реализована корпоративная светлая тема в стиле современных аналитических систем с акцентной палитрой VK.
   - Все статусы, категории и бейджи локализованы на русский язык.
   - Поисковая строка оптимизирована с помощью техники Debounce (250 мс) для предотвращения спама сетевыми запросами к базе данных.
   - Из формы создания обращения исключены избыточные поля: модель самостоятельно берет на себя рутину тегирования, оценки тональности и приоритета.

### Вариант А: Быстрый запуск через Docker (Рекомендуемый для проверки)

### Вариант Б: Локальный запуск без Docker (через uv)

```bash
# Клонирование и переход в папку
git clone <URL_РЕПОЗИТОРИЯ>
cd vk_public_analytics

# Установка зависимостей
uv sync

# Настройка .env (подключение к локальной PostgreSQL)
# DATABASE_URL=postgresql+asyncpg://postgres:123@127.0.0.1:5432/vk_support_db

# Запуск приложения
uv run uvicorn main:app --reload --port 8000
```

После старта веб-интерфейс доступен по адресу:
- Дашборд: `http://127.0.0.1:8000/`
